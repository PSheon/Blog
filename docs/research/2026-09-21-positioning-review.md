## 這份提案的問題（比「最像誰」重要）

### 1. 矩陣少了最該放的一排：真的在瀏覽器裡訓練模型的前輩

提案的結論是「在瀏覽器裡從零訓練模型……這個交集目前沒有人佔」。但「在瀏覽器裡訓練」這一格，十年前就有人了：ConvNetJS 的首頁就寫著「Open a tab and you're training」，有 MNIST、CIFAR-10、DQN 八個 demo；TensorFlow Playground 用的是為教學自寫的小函式庫（和 `lib/ml` 是同一個動機）；GAN Lab 在頁面裡訓練 GAN。這三個是這個站在 ML 這一側真正的祖先，提案一個都沒列。

它們和這個站的差別是真的，但要講對：它們是**工具或 demo 集，不是文章**——沒有論點、沒有「先壞給你看再修」的敘事、沒有量測紀律，而且都停在 2019 年以前。Transformer Explainer 則是另一種：跑真的 GPT-2，但只推論、只有一頁。

建議：矩陣補上這一排。懂行的讀者（也是最可能轉貼的讀者）第一眼會找這幾個名字；沒有，定位就顯得是不知道，而不是不一樣。

### 2. 「沒有 ML」這一格已經過期，而且他正往這邊走

Sam Rose 現在是 ngrok 的 developer educator，寫了 Prompt Caching 和 Quantization。Prompt Caching 那篇一路講到 tokenization、embedding 和 Transformer 的基本結構；Simon Willison 在 2025 年 12 月說它是「我看過最清楚、最容易懂的 LLM 內部入門之一」。

這改變兩件事。第一，矩陣裡他那一列的 ML 不是空格，是「有，解說型」。第二，也是比較重要的：**形式最接近、讀者最多的那個人，題目正在往這個站的領域靠**。他不訓練模型、不從零寫，這條界線目前還在，但「Sam Rose 沒有 ML」不能當作定位的前提。

另外兩個小事實：Retries 和 Queueing 不在 samwho.dev，是替 Encore 寫的（`encore.dev/blog/retries`、`/queueing`），samwho.dev 的網址是 404。訪談裡他確實說 Memory Allocation 那篇第一次用 GSAP、結果是「a tangled mess」，但**沒有**講後來怎麼整理；提案說「後來怎麼整理」，我在訪談裡找不到。

### 3. 「系統工程 ✓」是預支的

我對了 repo：十篇的標籤是 computer-vision、llm、generative、ai-agent、robotics、neuroevolution，**沒有任何一篇是系統工程**。矩陣最後一列把它打了勾，是把還沒寫的排程器那篇算進去了。這個站的規矩是數字要量過才寫；定位表也一樣，還沒有的東西不能打勾。

建議：那一格寫「計畫中」，或者等那篇發佈後再更新這張表。

### 4. 五個屬性的交集沒有人佔——這句話對任何站都成立

把自己的屬性全列出來，交集一定是空的：Ciechanowski 也是唯一一個「物理 + 全手寫 WebGL + 一年一篇 + 沒有任何框架」的人。空集合不是定位，只是描述。有資訊量的問題是：**哪一兩個差別是讀者感覺得到的，以及別人為什麼沒做。**

我認為這個站真正的差別只有兩條，而且都已經寫在首頁上了（「沒有 PyTorch，也沒有推論函式庫……就跑在你現在開著的這個分頁裡。文章裡的每個數字，都是實際量出來的。」）：

- **從零寫，而且在讀者的分頁裡真的訓練、真的跑。** Sam Rose 和 Ciechanowski 的模擬是手寫的，但不是學出來的；ConvNetJS 那一支會訓練，但不是文章。兩者兼有的，我查到的範圍內沒有。
- **每個數字都量過，腳本留在 repo。** Distill 是上一個認真做這件事的，它在 2021 年 7 月停刊，公告裡的原因是志工過勞和期刊形式撐不住，不是沒有讀者。

3D 是手段，不是賣點（Ciechanowski 的 3D 是論點本身，這個站的 3D 多半是舞台）。中文是讀者群的選擇，不是內容的差別。這兩項放進矩陣，只會讓真正的兩條差別變得不顯眼。

建議：定位表只留三欄——形式（文章／工具）、模型（手寫規則／跑別人的／從零訓練）、紀律（數字有沒有出處）。這三欄就足以把每個站分開。

### 5. 那句定位語是用別人定義自己

「Sam Rose 的形式，Ciechanowski 的嚴謹，內容是機器如何看、agent 如何行動。」當內部筆記可以，它幫你記得要向誰看齊。但它有兩個問題：讀者不一定認識這兩個人；認識的讀者會拿他們的標準來量你，而那兩個人一篇寫一到三個月（Sam Rose 自述）到半年以上（Ciechanowski 2019 年後 17 篇，平均四個月一篇）。

首頁現在那段話比較好：它只說這個站做了什麼，每一句都可以被讀者當場驗證。

建議：這句只留在 `docs/`，不要上站，也不要進 README。

### 6. 提案沒提的那件事：產量

這張表裡最刺眼的差別不是任何一格，而是節奏。Ciechanowski 十年 24 篇；Sam Rose 兩年半 11 篇。這個 repo 的第一個 commit 是 2026-09-18，三天後有十篇（002、003 的文字是舊站搬來的，儀器是新做的）。這是和 agent 一起寫才有的速度，它同時是最大的優勢和最大的風險：

- 優勢：那兩個人做不到「一個系列、同一套引擎、前後呼應」（001 的 CNN 是 005、010 的零件；`lib/ml` 一路長大）。系列感是這個站有、他們沒有的。
- 風險：他們每一篇都是打磨幾個月的單篇，會被轉貼好幾年。十篇三天，單篇的打磨度一定比不上；09-19 的編輯意見已經指出「004 之後每一篇都是同一個模板，連著讀會膩」。速度會放大模板化。

- 一個要 Paul 自己判斷的點：frontmatter 的日期在 3de3117 被重新產生過，現在從 2024-08 排到 2026-09，和 git 歷史不一致。站的招牌是「每個數字都量過」；會去翻 repo 的那種讀者，正是會轉貼這個站的讀者。日期怎麼標是作者的決定，我只是指出這兩件事放在一起會被看見。

建議：定位不要比單篇的精緻度（贏不了），比**系列**——同一套從零寫的引擎，一篇一個零件，最後組成一個會看、會想、會動的東西。這是首頁那條「看 → 想 → 生成 → 行動」的漸層已經在說的事。

## 對排程器那篇的意見

### 7. 不會撞題，但要當面承認他

我讀完的結果：他三篇的單位都是「一個個互不相干的請求」。

| | 他講了 | 他沒講 |
| --- | --- | --- |
| Retries | 緊迴圈重試的雪崩、固定延遲、指數退避（0.5 秒起、×1.5）、±50% 抖動 | 逾時、冪等、斷路器、重試預算、取消、相依 |
| Queueing | FIFO／LIFO／優先佇列／RED 丟棄；中位數與尾端延遲 | 相依、worker 池、截止期限、公平性、取消、進度 |
| Load Balancing | 輪詢、加權、動態加權、最少連線、PEWMA；p50／p95／p99 | 相依、優先順序、work stealing、故障、取消 |

「任務之間互相等待」他完全沒碰，空間是真的。但同一批讀者很可能讀過他。開頭直接連過去，對這篇有利：「一個請求怎麼排隊、怎麼重試、怎麼分流，Sam Rose 講過了。這篇講的是任務互相等的時候。」

### 8. DAG、加權進度、取消傳播，是三篇的量

這是 VLA 提案犯過的同一個錯（13 節、6 個儀器，最後拆了）。DESIGN §6：最多 10 分鐘、一節一個想法。三個主題各自都撐得起一個開場儀器和一個論點：

- DAG：關鍵路徑對總工作量——加 worker 到某個數就不再變快，讀者自己拉出那個膝點。
- 加權進度：為什麼進度條會卡在 99%——「每個任務一格」對「依估計工作量加權」，再加上估計本身有誤差。
- 取消傳播：取消一個節點，下游省下多少、已經做完的有多少白費——合作式對強制式。

建議：先只做一個。我會選**進度條**：它是三個裡唯一每個讀者都被騙過的東西，論點一句話說得完，而且 Sam Rose 的形式（一旋鈕一論點、帶著讀者做小目標）直接適用。

### 9. 它要怎麼接回主軸，得在定題前回答

這個站的主軸是「機器如何看、agent 如何行動」，首頁的四站是看、想、生成、行動。一篇純分散式系統的排程器，四站裡沒有它的位置，它會是第一篇離開主軸的文章，也會用掉「系統工程」這個還不存在的分類。

有一個接得回去的版本：排的不是 HTTP 請求，而是**一群 agent 的工作**——№ 009 的城市已經有三百個人和一個事件記錄，№ 010 的手臂有一串會失敗、要重試的步驟。「進度」「取消」「相依」在那裡都有現成的、看得見的對象。

建議：寫一頁提案，回答三件事再決定要不要做：一句話論點；三到四個儀器各自的一個旋鈕；它站在四站的哪一站。

### 10. 該向他借的，和他沒有的

借：每個模擬一個旋鈕一個論點；用小目標帶讀者（他在 Queueing 裡用「加 15 個請求」「丟掉 10 個優先請求」）；遊樂場放最後。這些和 DESIGN §6 本來就一致。

他沒有、這個站有的：模擬可以無頭快跑。№ 009 的「三種腦袋」那張圖，是讀者的瀏覽器在背景把三百個人跑兩天、當場畫出分佈。他的數字多半是敘述性的（「LIFO 的尾端延遲比較差」），這個站可以讓讀者按一下就看到一千次的分佈。排程器那篇應該從第一個儀器就用這件事。
