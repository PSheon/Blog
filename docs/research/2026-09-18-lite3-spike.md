# № 006 Lite3：可行性 spike

2026-09-18 · 研究 session（paul-d9）。選題見 [2026-09-18-article-006-topic.md](2026-09-18-article-006-topic.md)，Paul 已確認寫 Lite3。全部在 scratchpad 裡做，repo 只加了 `docs/research/` 底下的檔案，沒有裝任何套件到專案裡。

## 結論

**可行，而且沒有用到 onnxruntime。** 官方 policy 用手寫的 30 行 MLP 跑，配上 DeepMind 官方的 MuJoCo WASM，在 Node 裡走出來的軌跡和 Python MuJoCo + onnxruntime 一致到小數第二位，速度是即時的 29 倍。

## 量到的東西

腳本在 [lite3-spike/](lite3-spike/)（副檔名加了 `.txt`，避免被 lint／tsc 掃到）：`reference.py` 是 Python 參考實作，`rollout.mjs` 是 WASM 版，`sweep.mjs` 是擾動測試，`sweep-output.txt` 是它的完整輸出。

## 哪些互動真的有戲

每個設定跑 10 秒、指令 vx 0.5，單次執行（物理是確定性的，雜訊那組用固定 seed）。

- **速度指令**：要 0.25 / 0.5 / 0.8 / 1.2 / 2.0，得到 0.21 / 0.47 / 0.82 / 1.26 / 2.04 m/s。官方 deploy 把指令上限設在 0.8，但 policy 到 2.0 都跟得上。側移和倒退也可以。直走會慢慢偏（10 秒偏 0.5–2 m），沒有人在修正航向，這本身可以講。
- **側推**（推 0.1 秒）：150 N 撐得住，200 N 倒。門檻很清楚，適合做成「你推推看」。
- **蒙住一種感覺**（把那組觀測歸零）：
  - 陀螺儀：幾乎沒差。
  - 重力方向：1.5 秒後倒。
  - 關節角：0.36 秒就倒。
  - 關節速度：不倒，但**超速 2–3 倍**（要 0.3 得 0.59，要 0.8 得 2.52）。
  - 上一次動作：站著不動，完全不走。
  - 這一組最有教學價值：同一個網路，五種感覺的重要性天差地別。
- **觀測延遲**：每多 12 ms 慢一點（0.47 → 72 ms 時 0.26 m/s），到 72 ms 都沒倒。
- **感測雜訊**：±0.2 以下沒事，±0.4 走不太動，±0.8 立刻倒。
- **PD 增益**：Kp 10 站不起來（機身 0.20 m），Kp 100 反而走更快（0.8 m/s）；Kd 小走得快，Kd 大走得慢。policy 是在 Kp 30 / Kd 1 下訓練的，這是 sim-to-real 的好例子。
- **地板摩擦**：μ 從 1 降到 0.05 幾乎沒影響（0.47 → 0.44）。後來驗證過了（見下方「摩擦的結果是真的」），結果成立。

## 還沒做的

- **沒有在瀏覽器裡跑過。** Node 和瀏覽器用的是同一個 WASM，速度應該接近，但手機、記憶體、以及 Next.js 16 怎麼打包這個 ESM + wasm 都沒試。這一步要動 `package.json`，會和主 session 撞，等它那邊告一段落再做。
- 渲染沒碰：官方 demo 用 Three.js。專案現在沒有 3D 函式庫，要選 Three.js 還是自己用 canvas 畫線框，是一個要決定的事。
- 網格減面沒做。
- 只有平地。樓梯地形在 deploy repo 裡有，但這個 policy 是不是為樓梯訓練的沒有查。

## 給文章的初步骨架

1. 開場儀器：機器狗在走，讀者用搖桿給速度指令，旁邊即時顯示 45 個輸入和 12 個輸出。
2. 它沒有在這裡訓練：誠實說明訓練是在 Isaac Lab 用 GPU 做的，這裡只執行。這篇和前幾篇「在瀏覽器裡訓練」不同，要在開頭講清楚。
3. policy 就是三層矩陣乘法：把 19 萬個參數的 MLP 攤開，用 `lib/ml` 跑。
4. 它感覺得到什麼：45 維觀測逐組解釋，接「蒙住一種感覺」的互動。
5. 它不直接出力：動作 → 目標角度 → PD → 力矩，接 Kp/Kd 互動。
6. 推它：側推門檻。
7. 模擬和真機的差距：延遲、雜訊、增益不對會怎樣（都是量到的）。
8. 這和真的訓練差在哪：reward、domain randomization、teacher–student，留給之後有 GPU 的那一篇。

## 補充：摩擦的結果是真的

`lite3-spike/friction.py.txt`（Python MuJoCo）。接觸點實際用到的摩擦係數確實是設定值；腳掌著地時的水平滑動速度隨 μ 下降而上升，但 policy 撐得住：

| μ | 實際 vx（指令 0.5） | 著地腳的平均滑動速度 |
| --- | --- | --- |
| 1 | 0.47 | 0.12 m/s |
| 0.3 | 0.47 | 0.17 m/s |
| 0.1 | 0.46 | 0.22 m/s |
| 0.05 | 0.44 | 0.27 m/s |
| 0.01 | 0.24 | 0.47 m/s |

μ 0.1 再加 100 N 側推也沒倒；指令 1.5 m/s 時 μ 1 走 1.56、μ 0.1 走 1.31。合理的解釋是訓練時有做摩擦的 domain randomization（沒有查訓練設定，這是推測）。當互動的戲劇性不高，但可以配上「腳在滑」的讀數，拿來講 policy 的穩健性。

## 補充：出貨版本（凸包碰撞網格）重量一次（main session，2026-09-18）

`sim.ts` 補上了延遲、雜訊、摩擦三個旋鈕（邏輯同 `sweep.mjs`），`tests/lite3/sim.test.ts` 在 Node 裡用 `public/lite3` 的檔案重跑。延遲（0.42 / 0.34 / 0.26）、摩擦（μ 0.05 → 0.44、μ 0.01 → 0.24）、蒙住關節角（0.36 秒倒）、蒙住關節速度（1.26 m/s）、蒙住上一次動作（不走）都和上面一致。**有三個數字要改，文章草稿要跟著改：**

- **蒙住重力方向：1.02 秒倒**，不是 1.45 秒。原始網格換成凸包後，這種混沌的情況會變。文章要寫出貨版本的數字。
- **雜訊 ±0.4 不是「走不太動」而已。** 10 個種子各走 10 秒：4 個倒了（1.9–5.2 秒），6 個沒倒、速度 0.10–0.25。±0.3 全部沒倒（0.17–0.36）；±0.5 十個全倒（1.1–7.5 秒）；±0.6 以上多半 1 秒內倒。原本的 sweep 只跑了一個種子。
- **側推的門檻和步態相位、左右有關。** 走 2 秒後、每隔 60 ms 取 8 個時間點各推一次（0.1 秒），看 3 秒內倒不倒：

| 力 | 往 +y 推（8 次裡倒幾次） | 往 −y 推 |
| --- | --- | --- |
| ≤ 175 N | 0 | 0 |
| 200 N | 1 | 0 |
| 225 N | 4 | 0 |
| 250 N | 7 | 4 |
| ≥ 275 N | 8 | 8 |

所以「150 撐得住、200 倒」要改成：**175 N 以下推不倒，275 N 以上一定倒，中間看你推的時機和方向。** 這對儀器 04 是好事：同樣的力道多推幾次，結果會不一樣。

## 正式儀器的設計提案（等 Paul 確認後才動工）

全篇共用**一個**模擬器實例（一次載入 4.5 MB），每個儀器是同一隻狗的不同「面板」。讀者在第一個儀器按下「載入模擬器（約 4.5 MB）」後，後面的儀器直接可用；沒載入時每個儀器顯示同一顆按鈕與一張靜態截圖。

| # | 儀器 | 3D 畫面之外顯示什麼 | 讀者能做什麼 |
| --- | --- | --- | --- |
| 01 | 遙控 | 指令 vs 實際速度的兩條線 | 虛擬搖桿（手機）／WASD（桌機）：前後、側移、轉向；重置 |
| 02 | 它感覺到什麼 | 45 維觀測分六組的即時長條，12 個動作的長條 | 每組一個開關「蒙住」；顯示倒地時間或實際速度 |
| 03 | 動作不是力 | 一個關節的目標角度、實際角度、力矩三條線 | Kp、Kd 滑桿；標出訓練時的 30 / 1 |
| 04 | 推它 | 機身傾角的時間線，撐住／倒地的紀錄 | 力道滑桿 + 左右推；門檻約在 150–200 N |
| 05 | 真實世界沒這麼乾淨 | 指令 vs 實際速度、腳掌滑動速度 | 延遲、雜訊、地板摩擦三個滑桿 |

共同規則：倒地後 1.5 秒自動扶正；`prefers-reduced-motion` 時預設暫停；分頁不可見時暫停；離開視窗的儀器不渲染（全篇只有一個 WebGL context，canvas 隨目前的儀器移動）。
